# 可治理的工业 AI 代理：如何划分 LLM、数字孪生与人的责任

_最后更新：2026-10-01_

## 写在前面

设想有人对一个 AI 代理说：压缩机 C-204 出现异常振动，我们现在就该安排维护吗？

一个通用代理会怎么做？大概是去取振动数据，调一个异常检测模型，翻一下维护历史，然后建议安排检查。听起来挺像回事。可它多半不知道那个传感器有没有校准，压缩机是不是正跑在正常转速范围之外，模型适不适用于当前的负载工况，有没有维护锁定，提问的人有没有权限安排停机。

这类问题我想了很久。我的结论是，可治理的工业 AI 跟模型会不会说话关系不大，它是一套系统，推理、执行、验证、审批和责任各归各位。这篇笔记前一半讲我怎么一步一步搭这套系统，后一半讲为什么我认为代理必须跑在数字孪生之上。

## 第一步，挑一个工作流，别搞“AI 转型”

工业 AI 的起点是一项边界明确、价值可测量、责任归属清楚的工作流。泛泛的“AI 转型”做不出东西来。这篇我拿轮胎磨耗性能监测和仿真结果对比做例子。

工作流的价值得能量出来：工程师工时少了多少，试验周期快了多少，重复试验少了几次，数据可追溯性好在哪儿，报告出得多快，人为错误少了多少，历史知识用起来了没有。【待补：挑上面一项指标，给一个真实的前后对比数字】

评判一个受控 AI 系统，看它把工作流改进了多少。演示惊不惊艳，我不太关心。

## 第二步，把公司的知识整理成 AI 能用的结构

很多公司就是在这一步栽的。它们不缺数据，数据散在报告、电子表格、数据库、PLM 系统、试验系统、SharePoint 文件夹、仿真工具，还有专家的脑子里。

AI 系统需要一个领域上下文层。在工业 AI 里，这一层可以是本体、知识图谱，或者数字孪生。对轮胎工程来说，本体大致长这样：

```text
轮胎
 ├── 规格
 ├── 结构
 ├── 胶料
 ├── 胎面花纹
 ├── 刚度数据
 ├── 接地印痕数据
 ├── 实验室磨耗性
 ├── 道路磨耗结果
 ├── 车辆应用
 ├── 仿真模型
 └── 验证状态

车辆
 ├── 平台
 ├── 轴荷
 ├── 四轮定位
 ├── 工况循环
 ├── 路线
 └── 传感器数据

试验
 ├── 试验规程
 ├── 日期
 ├── 地点
 ├── 工程师
 ├── 原始数据
 ├── 处理后数据
 ├── 质量标记
 └── 已批准结论
```

大语言模型（LLM）不该去猜公司的数据是什么意思。它应该通过这个结构化的运营上下文去检索。

公司的竞争优势从这儿开始显现。基础模型谁都能买，本体只有你自己有。

## 第三步，画清楚谁能做什么

这是核心的设计步骤。一个受控 AI 系统必须说清楚：活儿怎么在 LLM、硬编码系统、人和模型基础设施之间分。

我的分法是这样。硬编码系统管规则、权限、工具、验证、执行和日志记录。人管判断、责任归属，以及高后果事项的审批。LLM 管推理、语言、综合和交互。模型基础设施里又有两样东西：模型网关按风险、成本、时延、隐私和数据敏感度选模型；受权限控制的 API 按模型选择、用户角色、数据敏感度和任务风险控制工具访问。

这一步要做四个决定：按风险等级给任务分类；决定 LLM、硬编码系统和人各自被允许做什么；通过模型网关把任务路由到合适的模型；只通过受权限控制的 API 向选定的模型开放工具。这四个决定别拆开做，它们是同一个问题：**谁被允许做什么，使用哪个模型，在什么条件下，依据什么证据，经过谁的审批？**

我最看重的一条是模型网关要排在受权限控制的 API 之前，因为选了哪个模型，信任边界就定了。外部前沿模型不该拿到跟本地模型或企业可控模型一样的工具访问权。面向公开数据的模型调用只能碰脱敏过的信息。跑在公司边界之内的本地模型可以碰更敏感的内部数据，但也只能通过受控的 API。

串起来就是：任务风险等级决定人、系统、LLM 的职责边界；模型网关选出允许使用的模型；受权限控制的 API 只开放该模型、该用户、该任务被允许使用的工具和数据。

### 先按风险给任务分级

职责边界取决于任务的后果有多大。低风险任务，LLM 可以自动做摘要、分类、起草或整理。中风险任务，LLM 可以给建议或起草，但必须经人工审核。高风险任务，LLM 可以提供证据和选项，最终决定由硬编码规则和人工审批控制。安全关键任务，LLM 可以辅助分析或解释，行动由经过验证的确定性模型和人的权限控制。

| 风险等级 | 示例 | LLM 的角色 | 硬编码系统的角色 | 人的角色 |
|---|---|---|---|---|
| 低风险 | 摘要一篇公开论文 | 摘要与整理 | 可选的来源核查 | 通常不需要 |
| 中风险 | 起草一份内部试验报告 | 起草与解释 | 检查来源、格式和数据质量 | 使用前审核 |
| 高风险 | 建议修改试验计划 | 提供证据和选项 | 验证输入、执行规则、记录决策 | 批准最终行动 |
| 安全关键 | 控制车辆制动或工厂设备 | 仅做解释或辅助分析 | 经过验证的确定性控制 | 拥有最终决定权 |

### LLM、硬编码系统和人，各干各的

LLM 不该变成控制系统。硬编码软件不该去模仿灵活的推理。人不该被迫手工去做软件能可靠自动完成的事。一个好的受控 AI 系统，会把每项职责放到合适的那一层。

LLM 这一层负责自然语言理解、摘要、对比、综合、生成假设、起草报告、解释和用户交互。

硬编码系统的清单长得多：权限检查、数据访问、确定性计算、执行经过验证的仿真、工具调用、数据质量规则、日志记录、审计记录、成本控制、安全约束，还有强制执行审批工作流。这张清单越长，我越放心。

留给人的是判断、责任归属、异常处理、技术审批、业务审批、涉及安全的决策，以及高后果行动的最终签核。

### 用模型网关，别绑死在一家供应商上

公司不该把每个工作流都绑死在一家模型供应商上。模型网关按风险等级、数据敏感度、成本、时延、所需的推理质量、隐私要求、部署环境、法规或客户约束来路由任务。

路由的结果大致是：公开信息任务给外部前沿模型；内部但非敏感任务给企业云模型；机密工程任务给本地开放权重模型、私有云模型或本地部署模型；常规结构化任务给更小、更便宜的模型；领域专属技术任务给微调模型、基于适配器的模型或本地领域模型；高风险决策任务 LLM 可以辅助，但必须有硬编码验证和人工审批；安全关键任务 LLM 不能直接采取行动。

模型网关让模型变得可替换。公司该拥有的是架构，订阅某一个模型算不上拥有什么。LLM 是系统中的一个组件。

#### 本地开放权重模型放在哪儿

本地开放权重 LLM 放在模型网关之内。碰到机密工程数据、内部试验结果、专有的仿真结果、胶料或结构信息、涉及客户敏感信息的车队数据，它很有用；对成本敏感的大批量任务、常规的摘要或分类、领域专属术语、基于内部文档的私有 RAG，也是它的地盘。

本地模型让公司对数据边界、部署环境、日志记录、访问控制、模型版本、微调和适配器、重复任务的成本、与内部工具的集成都有更强的控制。

但我得泼一点冷水：本地模型不会自动让系统变成受控的。架构薄弱的系统，换上本地模型照样薄弱。“内部数据加一个本地聊天机器人”这种搭法远远不够，却很容易让人产生已经安全了的错觉。

本地模型照样要跑在本体或数字孪生上下文、风险分类、硬编码规则、受权限控制的 API、日志记录和人工审批这套框架里。本地模型保护的是数据，硬编码的边界才是真正的控制系统。

### 工具只通过受权限控制的 API 开放

LLM 能调工具才有用，但工具必须由硬编码系统控制。LLM 不该随意访问数据库、仿真、生产系统或正式记录，它只能调用经过批准的 API，比如：

```text
read_test_data(test_id)
compare_model_prediction(tire_id, condition_id)
run_simulation(template_id, parameter_set)
generate_report(section_type, source_ids)
search_prior_validation_cases(tire_size, vehicle_platform)
create_engineering_review_ticket(issue_type, evidence_ids)
```

每个 API 都该带输入模式（schema）、权限检查、数据敏感度规则、验证逻辑、日志记录，必要时还有回滚机制和人工审批规则。API 的权限取决于选定的模型、用户角色、任务风险等级、数据敏感度、行动的后果，以及法规或客户约束。

把模型和 API 对起来看：公开信息任务走外部前沿模型，只能用公开搜索和引用 API；内部但非敏感任务走企业云模型，用受限的内部文档 API；机密工程任务走本地或私有模型，用经批准的试验数据和仿真 API；高风险工程任务走受控模型，只给只读 API，外加人工审批工作流；安全关键任务 LLM 不能直接采取行动，由经过验证的确定性系统和人的权限控制行动。

整条链的关键是：LLM 决定哪些信息或工具可能有用；模型网关决定哪个模型被允许对该任务进行推理；硬编码系统决定该工具调用是否被允许；受权限控制的 API 执行实际操作；风险等级要求时，由人审批。

### 回到轮胎：对比两条胎的磨耗预测

工程师问：“对比轮胎 A 和轮胎 B 在 Model Y 上的预测磨耗性能。”

硬编码系统检查权限，检索经批准的试验数据，运行经过验证的磨耗算法，执行数据质量规则，计算误差指标，开放经批准的工具 API，路由模型调用，并记录所有操作。LLM 理解问题，检索相关上下文，总结差异，识别缺失数据，起草对比结果。模型网关根据数据敏感度和任务风险选模型：公开的背景信息可以用外部模型，机密的轮胎试验数据可能需要本地模型或企业可控的模型。受权限控制的 API 只开放该选定模型、用户和风险等级被允许使用的、经批准的试验数据、仿真、对比和报告工具。最后由人审阅证据，判断结论在技术上站不站得住，批准最终建议。

这才是我说的受控 AI 边界：硬编码系统掌握控制逻辑；LLM 被放在正确的位置上，模型网关控制模型的暴露范围，受权限控制的 API 控制工具访问；在后果要求的地方，由人承担最终责任。

## 再往深一层：代理为什么需要数字孪生来支撑

上面三步里，“本体或数字孪生上下文”只是其中一层。下面想说清楚，为什么我把它看作让代理式 AI 在工业系统里变得可治理的那个支撑装置（harness）。工业 AI 代理需要的远不止一个 LLM、几个工具、记忆和护栏。

通用代理能推理、规划、调用工具、总结证据、协调工作流。工业代理还得跑在一个受治理的决策闭环里，有运行真值、模型有效性、安全约束、权限、不确定性处理、人工上报和可审计性。一句话：**工业 AI 代理 = LLM + 数字孪生支撑装置**。[【2】](#ref-2)[【3】](#ref-3)

### 通用代理可执行，工业决策要可治理

现代 LLM 代理有用，是因为它们能管多步工作流：选工具、检索信息、检查数据、写摘要、生成报告、跟人交互。这已经很强了。[【1】](#ref-1)

工业工作跟普通的工作流自动化不一样。代理可能影响维护、质量、过程控制、试验、保修决策、车队运营、安全评审，或者面向客户的技术声明。风险不只是答案可能错。更深的风险是答案没有建立在资产、流程、产品或车队的受治理状态之上。

通用的代理支撑装置回答的是：代理有没有正确调用工具，有没有遵循工作流，有没有给出看似合理的答案。

工业 AI 代理的支撑装置还得回答：数据有效吗？传感器校准了吗？模型在它的有效域之内吗？对于这台资产、这个工厂、这个角色、这个状态和这个风险等级，这一行动被允许吗？安全约束是在 LLM 之外检查的吗？不确定性露出来了吗？这个决策事后能重建吗？

差距就在这儿。通用代理框架让代理变得可执行，工业系统需要的是让决策闭环变得可治理。

回到开头那台压缩机。LLM 可以帮着推理那个情形，但它不该掌握运行真值。受治理的状态、模型有效性、约束、权限和可追溯性，该放在数字孪生支撑装置里，有了这些，建议才能用。

### 有工具访问权，不等于有授权

代理框架很会暴露工具。一个工具可以取遥测数据、查数据库、跑模型、搜文档、建工单，或者调外部系统。但拿到工具访问权，离拿到工业授权还远。

工具返回的结果需要上下文。这个数据是原始的、推断的、经校准的、过时的、有争议的，还是权威的？它描述的是哪台资产、哪个工厂、哪个流程状态、哪个时间窗口？用的是哪种单位制、采样率、时间戳约定和传感器质量规则？这个预测出自哪个模型版本、哪种校准状态？这个工具是只读的、会改记录的、可逆的，还是直接连着物理运行的？当前用户有权对这个结果采取行动吗？

通用的工具模式能描述怎么调一个函数，通常不会判断结果对某个特定工业状态是否有效。

比如一个振动异常检测工具对某台旋转设备返回了很高的异常分数。光有分数不够。系统必须知道振动传感器健康不健康，资产是不是处于正常运行工况，模型有没有针对该工况训练过，近期的工艺变更能不能解释这个信号，异常有没有超过维护阈值或安全阈值。这种授权该放在数字孪生支撑装置里，不该塞在 LLM 的提示词里。

### 工业记忆跟代理记忆是两码事

代理记忆通常指对话历史、检索到的文档、嵌入向量、摘要、先前的工具结果或反思，用来帮 LLM 把一项任务做下去。

工业记忆保存的是系统的受治理历史：资产拓扑与生命周期状态；遥测数据、报警、事件与运行历史；配置与工艺参数的变更；维护历史与工单；模型版本、校准状态与有效域；实验、干预、审批与人工覆盖；异常、故障、结果与事件记录。

这种记忆不能是代理内部一段松散的文本摘要。它必须时间对齐、有版本、可审计，并且跟物理系统绑在一起。

设想一个轮胎制造质量代理发现，一次工艺调整之后缺陷率变了。要紧的问题是设备、材料、方法、操作员行为、供应商来料、传感器校准、模型版本和运行工况里，到底哪些变了。代理记住了什么，排在这之后。这种运营记忆由数字孪生保存，LLM 基于它推理，治理它的必须是孪生。

### 护栏不等于安全约束

LLM 护栏有用。它能拦不安全的文本、强制输出格式、减少幻觉，把不确定的情况转给人。但工业系统需要的约束必须是确定性的、经过测试的，并且在 LLM 之外：运行包线、设备限值、工艺窗口、材料相容性规则、质量阈值、维护锁定、安全联锁、审批关口，还有客户、法律或法规方面的约束。

系统能直接编码并强制执行这些约束的时候，就不该让 LLM 从提示词里去推断它们。

代理建议提高某个工艺参数来改善良率。一条看似合理的建议不够。支撑装置得检查新值是否还在工艺窗口之内，有没有违反设备限值，有没有改变产品质量风险，模型在那个区域有效不有效，要不要人工审批。所以我一直说数字孪生是围绕代理的授权边界，光把它当 LLM 的上下文，太小看它了。

### 支撑装置手里到底拿着什么

数字孪生支撑装置是一个受治理的运行基底，它调节 AI 代理在工业系统里怎样观察、推理、仿真、验证、行动、上报和记录决策。

它手里应该有：受治理的资产、流程、产品、试验或车队状态；传感器健康状况与数据质量元数据；基于物理的模型与数据驱动的模型；模型注册表、模型版本、校准状态与有效域；不确定性估计与模型间分歧信号；仿真与假设情景分析的执行；确定性的运行约束与安全规则；基于角色、资产、工厂、状态和风险的权限；人工上报与审批工作流；溯源、审计日志与决策轨迹；把建议与结果连接起来的评估记录。

LLM 还是有价值的。它可以提出下一个诊断问题、比较各种假设、解释权衡、起草建议、总结证据、协调工作。但它应当通过孪生来推理，别绕开它。

这个孪生不必是完整的工厂孪生。工厂孪生、生产线孪生、流程孪生、资产孪生、产品孪生、试验孪生、车队孪生都行。做第一个概念验证，我会选一个小而成熟的流程孪生，不选庞大的工厂孪生，因为小的那个状态、约束、不确定性和授权边界更容易说清楚。

分工就一句话：LLM 代理负责推理、规划、解释、协调、提议；数字孪生支撑装置负责授权、验证、约束、仿真、上报、记录；工业系统负责执行、测量、维护、生产、控制。代理可以提请求，支撑装置决定什么是有效的、允许的、安全的、可追溯的，以及需要上报的。

### 这个公式防的是两个错

**工业 AI 代理 = LLM + 数字孪生支撑装置**这个写法有用，是因为它防住了两个常见的错。

第一个错是把 LLM 当工业大脑。LLM 是一个推理与交互组件，它不是运行真值的来源。

第二个错是把数字孪生只当又一个工具。仪表盘、仿真模型或 RAG 数据源都不够。只有当孪生治理着状态、有效性、不确定性、约束、权限、溯源和可审计性时，它才成为支撑装置。

当前的 AI 代理支撑装置管的是代理的一次运行，数字孪生支撑装置管的是工业决策闭环。这个区分要紧，因为工业 AI 的失败很少只是推理失败，更多是治理失败：过时的数据、缺失的上下文、无效的模型假设、薄弱的授权边界、不清晰的审批、分散的可追溯性，或者被掩盖的不确定性。

### 它不是万能药

数字孪生支撑装置不会自动让工业 AI 变安全。孪生可能不完整、过时、过度自信、校准不良，甚至是错的。一个做得很精致的孪生，要是掩盖了缺失的数据或不确定性，还会制造出虚假的权威。这一点我最担心。

它的价值在架构层面。它给工业 AI 系统一个把信任要求摆明的地方：当前受治理的状态是什么？哪些模型在此处有效？哪些假设在生效？还剩哪些不确定性？哪些行动被阻止？需要哪些审批？必须保存哪些证据？

它不会取消工程判断。它给工程判断一个受控的系统去运作。

## 写在后面

把这两半合起来，我真正想说的只有一个公式：工业 AI 代理 = LLM + 数字孪生支撑装置。LLM 出推理、规划、语言、解释和协调；数字孪生支撑装置出工业授权，也就是受治理的状态、模型有效性、安全约束、权限、不确定性处理、上报、溯源、可审计性和评估。一个能给出看似合理答案的代理，和一个其建议可以被信任、被限定、被批准、被重建的工业 AI 代理，差别就在这里。

有几处我没有把握。三步法里第一步“挑一个工作流”说得轻巧，可到底多小的工作流算够小、多大算失控，我没有可靠的判据，手头也没有一个从头跑到尾的完整案例可以拿出来。【待补：一个真实走完三步的工作流案例，哪怕只是内部试验】 另外，模型网关放在 API 之前这一条，我自己也在想它会不会把路由逻辑做得过重，让小团队根本搭不起来。

现在有人拿代理架构来问我，我先看一件事：当代理行动时，由什么来掌握运行真值？答案是“LLM”，这个架构就是脆的。答案是“一个受治理的数字孪生支撑装置”，它才有机会在生产环境里真的有用。至于“我们该用哪个代理框架”，我已经不太问了。
